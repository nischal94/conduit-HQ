Conduit · the demo story

Two tools instead of eight hundred manuals

Written 2026-07-13, the day the §4.2 token demo merged (PR #33 → main 08cb658). Every number below is live-measured — the source of truth is demo/token-demo.json, regenerated by node scripts/token-demo.mjs. Base material for product demos and investor decks.

The story, as you'd tell it in a demo

Claude Desktop is an agent that can be handed tools. The normal way to hand it 800 tools is to paste all 800 instruction manuals into its head before every single conversation — 133,450 tokens of manuals it mostly never uses. That's slow, expensive, and it drowns the model.

Conduit's pitch is: put one adapter between the agent and everything else. The agent gets handed exactly two things — execute ("write a bit of code that calls whatever tool you need") and check_execution ("check on a call that's still pending"). That's 505 tokens, ever, no matter whether Conduit fronts 8 tools or 8,000. When the agent's code actually calls github_create_issue, Conduit looks that one tool up in its catalog, checks policy (allow? pause for your approval? block?), attaches the credential outside the sandboxed code so the model never sees it, makes the call, and records a trace. Gate one is simply proving this works with the real chat app rather than our test harness: Desktop connects, sees the two tools, and drives one real call through the whole pipe.

The demo upstream is a stand-in for "everything else" — 800 fake-but-realistic tools served by a tiny local script, so you get the full experience with zero real accounts and zero real credentials.

Is the config change safe? Yes — here's exactly what it touches

  • claude_desktop_config.json belongs to the Claude Desktop app (the chat client), not to Claude Code. Nothing in ~/.claude/ — your settings, hooks, sandbox, skills, this whole workflow — is read from or written to that file. Your CLI setup is untouched.
  • The edit adds one entry that says "when Desktop starts, also launch this local command." Deleting the entry (or renaming it) fully undoes it. Desktop's other MCP servers, if any, are unaffected.
  • Everything runs on your machine: the upstream binds to 127.0.0.1 only, no network leaves the laptop, and the master key just encrypts Conduit's local database file.
  • One real footprint to know about: add-mcp writes a small SQLite database (default ~/.conduit/conduit.db). To keep the demo fully throwaway, set CONDUIT_DB=<repo>/.demo/conduit.db in both the add-mcp command and the Desktop config's env — then cleanup is deleting one folder.
  • One known wrinkle we'll hit live: the upstream picks a fresh port each start, so if you restart it, the stored source points at the old port and calls will fail until we re-run add-mcp --replace. Expected, not a bug — I'll handle it when we walk it.

So: purely a demo, fully reversible, no credentials at risk, no effect on your workflow.

My honest thesis on the product

The direction is right, and the reason is that Conduit sits on three pains that get worse as agents get better, not better:

  1. Token bloat is structural. Every company adding MCP servers rediscovers that tool schemas eat the context window. We just proved the fix works at 264× — measured, not claimed — and progressive disclosure is the kind of advantage that compounds as catalogs grow.
  2. The credential boundary is the actual moat. Lots of people can build an MCP proxy; the hard, defensible part is what we've spent most of the project on — secrets that never enter the sandbox or the model, a policy engine with a human approval seam the agent cannot approve through, and a trace that redacts at write time. That's a security product, and enterprises pay for exactly that when they let agents touch real systems.
  3. The approval seam is the adoption unlock. Nobody deploys an agent that can delete production data unsupervised. "Safe tools run, risky tools pause for a human" is the story that gets Conduit into rooms the token demo alone wouldn't.

What I'd flag honestly: the plumbing (proxying, normalizing) will commoditize — MCP gateways are appearing everywhere — so the differentiation has to stay on the boundary/policy/trace side, and the biggest gap between "engine" and "product" is still ahead of us: the web console and onboarding UX, which is where non-builders will judge it. Also, everything so far has been validated by tests and reviews; gate one is the first time a real client touches it, and I expect it to surface exactly the kind of rough edges (like that port wrinkle) that tests structurally can't.

Am I happy with how we've built it? Genuinely yes — the walking-skeleton discipline (invariants pinned before features, adversarial reviews with a defined stop line, human-named merges) has produced a codebase where the security claims are tested facts, not aspirations. That's rare at this stage and it's the right foundation for what this product claims to be. Next session: gate one, live.
